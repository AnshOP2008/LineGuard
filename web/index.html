From machine signals to an inspection priority

Each step runs online on one-second data, uses only the past, and keeps its reasoning visible to the person who has to act on it.

  1. Sense

    Eight signals on the pump: two vibration, motor current and voltage, loop pressure, flow, motor and fluid temperature. In the live service they arrive over MQTT .

  2. Learn the healthy baseline

    The first 400 seconds after start-up are the reference. Each signal is judged by what is physically meaningful: level for flow, pressure and vibration; rate of change for temperatures, which drift during warm-up.

  3. Detect

    A Watch state flags a signal drifting toward its limit before any alarm. Every feature gets a calibrated limit from the baseline. An alarm needs the evidence outside that limit, holds with hysteresis, and clears when the evidence returns. A data-quality check catches stuck and dead sensors.

  4. Diagnose

    A relationship model predicts each sensor from the others, and paired sensors check each other. The verdict is machine fault, sensor fault, or unconfirmed with a two-minute check to settle it. On the hydraulic rig, a second model names the component and its wear grade.

  5. Act

    Each alert becomes a prioritised work order with a checklist, tracked from Open to Closed. Closing it is checked against the data. A line simulation shows what waiting would cost downstream.

What is real and what is simulated
  • Real: every signal on the Monitor page except the two injected scenarios is real SKAB data, replayed.
  • Real: component diagnosis uses the real UCI hydraulic rig recordings.
  • Injected: sensor faults are added to healthy data and marked wherever they appear, because SKAB has no labelled sensor faults.
  • Simulated: the four-stage line and its costs. They show the decision, not a measured saving.
  • Limits: one lab rig with short runs; component diagnosis is validated on a different rig than the live stream; no plant pilot yet.
  • Not claimed: predictive maintenance and multi-sensor monitoring exist already. The contribution is the combination, measured against clear baselines.
Run it yourself

The repository regenerates every number on this site:

pip install -r requirements.txt
python -m lineguard all      # download, evaluate, export
python -m lineguard serve    # live API + this dashboard

Live mode streams sensor readings to the FastAPI service, which runs the same detector online and stores operator feedback in SQLite.

Questions we expect

It needs 400 seconds of healthy data after every start?

Yes. That is SKAB's protocol, and it makes LineGuard work on a new machine with no history. In a plant the baseline would be stored per machine and operating point after commissioning, then reused.

Why does it miss 3 of 34 faults when T²+Q catches all 34?

T²+Q also raises 125 false alarms; an alarm that is always on catches everything. LineGuard trades three quiet faults for 14 times fewer false alarms. The low-false-alarm mode and the limit margin let a plant choose its own balance.

Can it name the broken part on this pump?

No. SKAB records no part labels, so on the pump LineGuard names the signals involved and a likely area. Part-level diagnosis is shown separately on a hydraulic rig that has part labels.

Are the sensor faults real?

No public dataset labels sensor failures, so they are injected into real healthy recordings and marked as injected everywhere. All machine faults are real.

Is the cost figure real?

No. The line and its costs are a simulation with assumptions you can edit. It shows the decision an alert supports, not a measured saving.

Why not just use a deep neural network?

We trained the leaderboard's best ones. With the published look-ahead removed they score lower and alarm about a minute later, and they cannot explain an alarm to a technician.
